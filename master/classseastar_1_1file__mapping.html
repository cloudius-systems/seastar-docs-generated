seastar::file_mapping Class Reference
File Input/Output

Detailed Description

A memory mapped region of a file.

Represents a memory region created by seastar::file::mmap().

Warning
This API is strongly discouraged for general-purpose file I/O. Accessing file-backed memory mappings relies on the kernel page cache and can trigger major page faults. These faults will silently block the Seastar reactor thread, bypassing Seastar's I/O scheduler and severely degrading overall system performance. Seastar applications should prefer O_DIRECT DMA interfaces (e.g., dma_read) for persistent storage.

This facility is provided specifically for shared memory use cases (e.g., mapping files on tmpfs or shm), where data resides entirely in RAM and blocking disk I/O is not a concern.

Because munmap requires acquiring kernel mmap_sem locks, it cannot be executed synchronously in a destructor without risking blocking the reactor. Therefore, the user must explicitly await the asynchronous unmap() method before this object is destroyed.

◆ flush()

future seastar::file_mapping::flush ( )
noexcept

Flushes changes made to the in-core copy of a file that was mapped into memory using mmap(2) back to the filesystem by calling msync(2).

This method is executed asynchronously on the reactor's thread pool, as msync blocks until the dirty pages are written to the underlying storage.

Note
For the primary use case of this class (shared memory via tmpfs or shm), calling flush() is strictly unnecessary as the data resides entirely in RAM.

This method is provided primarily for testing or rare edge cases where mapped memory access is mixed with Seastar's O_DIRECT I/O. Because dma_read() bypasses the kernel page cache, dirty mapped pages must be explicitly synced to the backing device before a DMA read will see the modifications. Doing this on persistent storage in production is strongly discouraged.

future seastar::file_mapping::unmap ( )
noexcept

Unmaps the file mapping asynchronously.

This must be called exactly once before the object is destroyed.

Postcondition
The file mapping is unmapped and the object is in an uninitialized state (i.e. get() returns nullptr and size() returns 0).
