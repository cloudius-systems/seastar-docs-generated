seastar::coroutine::experimental::internal::unbuffered::generator< Ref, Value > Class Template Reference

Detailed Description

template<typename Ref, typename Value>
class seastar::coroutine::experimental::internal::unbuffered::generator< Ref, Value >

unbuffered generator provides a simple async API for generating values.

generator has 2 template parameters:

  • Ref
  • Value

From Ref and Value, we derive types:

  • value_type: a cv-unqualified object type that specifies the value type
  • reference_type: the reference type returned by operator()
  • yielded_type: the type of the parameter to the primary overload of yield_value in the generator's associated promise type

Under the most circumstances, only the first parameter is specified: like generator<meow>. The resulting generator:

  • has a value type of remove_cvref_t<meow>
  • has a reference type of meow, if it is a reference type, or meow&& otherwise
  • the operand of co_yield in the body of the generator should be convertible to meow when meow is a reference type; when meow is not a reference type, the operand type should be const meow&

Consider following code snippet:

generator<const std::string&> send_query(std::string query) {
auto result_set = db.execute(query);
for (auto row : result_set) {
co_yield std::format("{}", row);
}
}

In this case, Ref is a reference type of const std::string&, and Value is the default value of void. So the value_type is std::string. The generator returns a reference to the yielded string.

But if some rare users want to use a proxy reference type, they should use the two-argument generator, like generator<meow, woof>. The resulting generator:

  • has a value type of woof
  • has a reference type of meow

For instance, consider following code snippet:

generator<std::string_view, std::string> generate_strings() {
co_yield "[";
std::string s;
for (auto sv : {"1"sv, "2"sv}) {
s = sv;
s.push_back(',');
co_yield s;
}
co_yield "]";
}

In this case, Ref is std::string_view, and Value is std::string. So we can ensure that the caller cannot invalidate the yielded values by mutating the returned value, as std::string_view is immutable. But in the meanwhile, the generator can co_yield either a std::string_view or a std::string. The caller receives values as std::string_view.

This unbuffered generator implementation minimizes ping-pong overhead by:

  1. Avoiding the scheduler when preemption is not needed - directly transferring control between producer and consumer coroutine handles
  2. Only going through the scheduler when need_preempt() indicates it's time to yield to other tasks
  3. Yielding elements in-place via pointer - zero copy/move overhead

However, the unbuffered design inherently requires one coroutine suspension/resumption pair per yielded value (producer suspends on co_yield, consumer suspends on co_await). While direct handle transfer avoids scheduler overhead, the suspension/resumption itself still impacts icache and branch prediction in high-throughput scenarios.

Performance tradeoffs:

  • Use unbuffered generator for latency-sensitive code or when element moves are expensive
  • Use buffered generator (third template parameter) for throughput-critical code where move cost is acceptable

The buffered generator amortizes suspension overhead by batching: elements are moved into an internal buffer until it's full or need_preempt() returns true. The consumer then drains the buffer without coroutine suspensions (tight loop). This trades per-element move overhead for reduced suspension overhead, similar to how flat_mutation_reader batches mutations.
